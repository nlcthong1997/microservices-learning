POST /orders/sync
HTTP Sync cơ bản — không có timeout, không có retry, không có circuit breaker.
Vấn đề của Sync không có bảo vệ
Nếu inventory-service không phản hồi → request treo vô thời hạn. 1000 user đồng thời = 1000 connection treo → order-service crash. Dùng /sync-resilient trong production.
✓ Thành côngĐặt hàng thành công
✗ Hết hàngqty=999 → out of stock
POST /orders/sync-resilient
3 lớp bảo vệ: Circuit Breaker → Retry → Timeout (3s per attempt, max 3 retries).
Thứ tự bảo vệ
Circuit Breaker kiểm tra trạng thái trước. Nếu OPEN → fail ngay (<1ms).
Nếu CLOSED → Retry thử lại khi gặp lỗi tạm thời.
Mỗi lần retry có Timeout 3s. Tổng worst-case: 3×3 = 9s.
✓ Thành côngNormal call <200ms
⏱ TimeoutTRIGGER-SLOW → 504 sau ~9s
Inventory giả vờ chậm 5s. Order-service timeout sau 3s × 3 lần retry = 9s rồi trả 504.
⚡ Circuit BreakerTRIGGER-ERROR ×4 → CB OPEN
Click 3 lần → failures tăng → lần thứ 4 circuit OPEN → fail ngay <1ms (không chờ timeout nữa).

POST /orders/async
RabbitMQ Async + SAGA — trả 202 ngay, xử lý ngầm qua exchange → queue → inventory → payment.
Fire-and-forget + Eventual Consistency
Client nhận 202 Accepted (~2ms) mà không biết kết quả cuối. Inventory reserve → payment charge (RabbitMQ SAGA).
Xem log các service để theo dõi luồng xử lý tiếp theo.
✓ Happy pathReserve + payment success → confirmSale
✗ Hết hàng → DLQqty=999 → nack → Dead Letter Queue
↩ SAGA RollbackFAIL-PAYMENT → reserve OK → payment từ chối → rollback
Inventory reserve thành công (stock có hàng). Payment-service nhận FAIL-PAYMENT → từ chối → publish saga_events → inventory rollback.

POST /orders/sync-grpc
Gọi inventory-service qua gRPC (HTTP/2 + Protobuf binary) thay vì REST. Response có thêm field protocol: "gRPC".
Tại sao gRPC nhỏ hơn REST?
REST: {"productId":"IPHONE-15","quantity":1} → ~215 bytes text
gRPC: Protobuf binary → ~30 bytes
Nhỏ hơn ~85%, không cần parse JSON, IDE biết type ngay lúc viết code.
✓ Thành côngCòn hàng — response có protocol:gRPC
✗ Hết hàngqty=999 → 400
✗ NOT_FOUNDINVALID-SKU → gRPC status 5 → HTTP 404
POST /orders/kafka-saga
Choreography SAGA qua Kafka — 3 service phối hợp không gọi nhau trực tiếp.
Luồng SAGA
order-service → [order-events] → inventory (reserve)
→ [inventory-events] → payment (charge)
→ [payment-events] → inventory (confirm / rollback)

Mở Dashboard tab Kafka SAGA để thấy animation packet.
✓ Happy pathĐặt hàng → reserve → payment OK → confirm sale
✗ Out of stockFAKE-SKU → inventory.failed → SAGA dừng
↩ SAGA RollbackFAIL-PAYMENT → reserve OK → payment fail → rollback
Kịch bản quan trọng nhất — compensating transaction. Sau khi chạy, xem DB: reserved phải về 0.
